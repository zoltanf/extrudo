# P0-03 solver spike

Throwaway code for roadmap task **P0-03**. It measures the planegcs sketch
solver (FreeCAD's PlaneGCS compiled to WASM, `@salusoft89/planegcs` 1.2.0) in
Node and in the browser, and it produced
[ADR-0002](../../docs/adr/0002-sketch-solver.md). Nothing here is imported by
the app. The production adapter is P1-03.

Results are in [`results/summary.md`](results/summary.md) (generated by
`node src/node/report.ts`), with the raw numbers in `results/*.json` and
screenshots in `results/browser-*.png`.

## What it measures

- **The task's scenario** (browser, `index.html`): a rectangle with
  coincident, horizontal/vertical and width constraints; drag its free corner
  at 60 fps; read DOF and the conflicting constraints after adding a second
  width.
- **Scale** (`src/sketches.ts`): fully constrained sketches of 50, 100, 200 and
  500 entities (lines, arcs and circles; points aren't counted). One cell is a
  rectangle, a hole and a slot with tangent arcs, all dimensioned: 9 entities.
  - `anchored`: every cell is dimensioned from the fixed origin, so the sketch
    is many independent components (the usual case).
  - `chained`: each cell is dimensioned from the previous one, so the whole
    sketch is one coupled system (the worst case; a long closed outline such as
    a gear profile behaves like this too).
  - `coincident` joins curves with coincident constraints (how FreeCAD and
    Fusion store sketches); `shared` makes joined curves reference the same
    point (what an adapter could do before solving).
- Per configuration (`src/bench-core.ts`): build, first solve from a perturbed
  start, DOF, a re-solve with nothing changed, a driving-dimension change, drag
  steps (temporary constraints bound to two sketch parameters, no rebuild),
  drag steps that rebuild the system, a conflicting dimension, and the three
  algorithms.
- **Per-component solving** (`src/components.ts`, `benchComponents`): split the
  sketch into independent components and keep one planegcs system each.
- **Builds** (`planegcs-build/`): the npm build and three of our own.
- **SolveSpace** (`src/slvs-bench.ts`): the `slvs` npm package on the same
  sketches, for comparison.

## Running it

This package is **not** part of the pnpm workspace.

```sh
cd spikes/p0-03-solver
pnpm install --ignore-workspace
planegcs-build/build.sh growth    # and modern, fast (Docker; ~2 min for the first)
npx tsc -p tsconfig.json
node src/node/check-sketch.ts     # the generated sketch solves to DOF 0
node src/node/check-builds.ts growth modern fast   # builds agree with npm's
node src/node/bench.ts            # BUILD=growth for our build → results/node-<build>.json
node src/node/components.ts       # per-component solving → results/components-<build>.json
node src/node/compare.ts growth modern fast        # → results/compare.json
node src/node/slvs.ts 50          # SolveSpace comparison
npx vite build && node src/browser/measure.ts      # → results/browser.json + screenshots
node src/node/report.ts           # → results/summary.md
pnpm dev                          # http://127.0.0.1:5175/?build=fast
```

The chained 500-entity cases take minutes each on the single-system builds.

## Our planegcs builds

`planegcs-build/build.sh` clones planegcs at the tested commit, generates its
C++ bindings in a Node 20 container (its tree-sitter dependency doesn't build on
Node 26), applies one of the patches and compiles:

| Variant | Toolchain | Changes |
|---|---|---|
| `growth` | upstream image (emsdk 3.1.45) | `ALLOW_MEMORY_GROWTH` |
| `modern` | `emscripten/emsdk:latest` (6.0.10) | + `-msimd128` |
| `fast` | same | + DogLeg Gauss step `LeastNormLdlt` (a FreeCAD option) instead of `FullPivLU`, and column-pivoting instead of full-pivoting QR in the SQP step (`qp_eq`) |

All three solve the test sketches to the same geometry as the npm build (within
1e-11 mm, `check-builds.ts`).

## Findings in short

See the ADR for the decision. The measured facts:

- **The npm build has a fixed 16 MB heap**: it aborts with out of memory at
  about 100 entities in one system. Building with `ALLOW_MEMORY_GROWTH` fixes
  that.
- **Cost grows steeply with the size of one system.** The diagnosis (the QR
  decomposition that gives DOF and conflicts) runs whenever constraints are
  added or removed, over the whole system, and costs 245 ms at 200 entities and
  5 s at 500. The solvers use dense matrices, so a drag step in one coupled
  component costs 19 ms at 100 entities, 130 ms at 200 and 4.5 s at 500.
- **Per-component solving makes size irrelevant for the usual sketch**: at 500
  anchored entities (56 components) a drag step is 0.16 ms, a constraint edit
  0.8 ms, opening the sketch 42 ms. Even the npm build handles it.
- **In the browser**, the task's rectangle drags at 60 fps (0.2 ms per solve),
  and so does the 500-entity anchored sketch (0.7 ms). A 200-entity coupled
  component drags at 12 fps even with the `fast` build.
- **Drag without rebuild**: temporary coordinate constraints bound to two sketch
  parameters, updated per frame. Changing parameter values doesn't re-run the
  diagnosis; rebuilding the system does (2.4× to several hundred times slower).
- **Endpoint tangency must use `angle_via_point`** (as FreeCAD does). The
  simpler `tangent_la` + coincident endpoints is degenerate at the solution, so
  the diagnosis reports false redundancies and a wrong DOF.
- **Conflicts** are reported as the group of constraints involved, which
  always contains the new one: exactly the two widths on the rectangle, 4–5
  constraints in the generated sketches.
- **SolveSpace (`slvs` 3.1.0-dev.14)** was slower (88 ms first solve at 54
  entities against 8.6 ms), ran out of memory on the chained 54-entity sketch
  and at 100 anchored entities, and its `tangent()` aborts. Not pursued.
- The `modern` toolchain with SIMD is 10–17% faster on coupled systems; the
  `fast` patches another 1.4–1.6×.
