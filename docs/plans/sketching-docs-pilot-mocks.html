What a page looks like

These are working mocks in the docs site's look. Try them: they show the three kinds of visual the pages will use.

interactive for anything that responds to what you do (constraints, dragging, switches). static for something seen at a glance (glyph tables, click steps). clip for the real app in motion (the existing tooltip clips, plus new ones).

 extrudo.org/docs/sketching/#free-fixed-conflict

Free, fixed, conflict interactive

The colour of a curve tells you how much it can still move. Drag the blue corner, then turn the constraints on one by one and watch the counter.

Blue: free · ink: fixed · red: conflict. The rectangle tool already holds the corners together and the sides level, so a new rectangle has 4 DOF left.

The widget is drawn at build time in its starting state, so without JavaScript (and in print) it shows as a still picture. The one docs script makes it respond.

How the widgets work

MarkdownA fenced block names a widget:
```widget dof```. Pages hold no HTML or script.
→
BuildThe docs build looks the name up in a fixed list; an unknown name fails the build. It writes the widget's starting state as SVG into the page.
→
BrowserOne script, served from the site itself (docs-widgets.js), wakes each widget up. Without it, the still picture stays.
  • Same pattern as the landing page's tray toy: a pure model file (no DOM, unit-tested) plus a small file that wires it to the page.
  • No solver and no WASM in the docs: each widget is a scripted scene with its own small rules (the DOF rectangle knows its four unknowns). The real solver is many MB and would need the content policy loosened for WASM.
  • Colours come from the app's sketch colours; both themes; animation stops under reduced motion; keyboard works for every switch and handle.
  • Headings get anchors (#free-fixed-conflict), which the docs site lacks today. F1 needs them.
  • This needs an ADR: it amends ADR-0080 and the "no script in docs pages" rule from ADR-0057. Rejected options: embedding the real app in a frame (heavy, slow, fragile), and pictures only (no interaction).

Decisions

1. Static diagrams
  1. Drawn SVG in the app's colours: crisp, follows light/dark, easy to edit; may drift a little from the real UI. recommended
  2. Screenshots recorded from the app (pnpm demos): always the real UI, but one theme only and they need re-recording when the UI changes.

With 1.1, the palette and the dialogs would still be real screenshots, since there the real UI is the point.

2. Widget direction
  1. The mocks above are the direction: app-like switches, grid background, the app's sketch colours. recommended
  2. Something else: tell me what to change before the briefs are written.
