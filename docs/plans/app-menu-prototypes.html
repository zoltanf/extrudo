One menu instead of two

The Help menu folded into the app menu, with the quick toggles on its root. The refined direction comes first; the four starting points follow. The mockups are clickable: toggles flip, the Theme control re-themes its own mockup, the rail's controls show their tooltips on hover.

Direction

Wide panel, refined

Prototype 2 with the owner's changes. The rail is one line of icon switchers: the mouse preset first as a six-way segmented control, a divider, the three toggles, a divider, and Theme. The rail sets the panel's width; nothing stretches. Each control carries the app's tooltip, with the preset's bindings as the hint, so the icons never have to explain themselves. The columns are fixed at two. Search… leads the App column, About Extrudo sits under Settings…, and the footer is the version strip: update state at a glance, the update check and GitHub as links.

  • Rail: Mouse (6) · toggles (3) · Theme (3). Hover any of them for its tooltip: name on top, the bindings or state as the hint.
  • Mouse presets in order: Crank, Spindle (the default, checked), Glide, Blender, then the new Slicer (left-drag orbits, right-drag pans, Shift+left-drag selects; menu entry only for now, the behaviour comes later) and Trackpad.
  • App column: Search…, Settings…, About Extrudo, then Close design and Quit.
  • Learn column: Help for <tool> first, named after the tool last hovered or active (here Extrude) and absent when there is none; then User Guide, Tutorial (the built-in five steps), Online Tutorials, Examples, Tool Reference.
  • Version strip: dot and word for the update state (never colour alone), Check now on the desktop app only, GitHub everywhere.

Open points, by number:
1. Preset icons: a mouse with the orbit button filled (middle for Spindle, right for Crank, left for Slicer), pan arrows for Glide, a modifier key for Blender, a pad for Trackpad. Keep, or label the active one with its name?
2. Quit and Close design: keep both in the App column, or move them to the strip's right end as a last resort?
3. The strip's "Up to date" needs the updater's state on the desktop; the web build shows the version alone.

The four starting points

Kept for comparison. Prototype 2 is the one the direction above grew from.

1

One list, toggle strip on top

The smallest change. The two menus become one list in the familiar width. Theme and the three behaviour toggles leave their submenus and sit horizontally at the top, where a flick of the eye reads their state. Mouse controls keeps its submenu because each preset needs its description line. Settings… is the only dialog item left, with Plugins and the marking menu inside it.

  • Keeps every existing menu primitive, so it is cheap to build.
  • State visible without opening anything: the strip is the status.
  • Long: 15 rows plus the strip, about 600 px. Fits a 768 px tall window.

Lowest risk. If the length bothers you, prototype 2 or 4 trades it for width.

2

Wide panel, two columns

The menu grows into a 480 px panel. A rail across the top holds every quick setting in one horizontal line: Theme as three icons, the three toggles as icon buttons, the mouse preset as a chip that opens its chooser. Below, the app's own items on the left and everything you learn from on the right. A grey footer carries the version, updates, GitHub and About, the way an About box would.

  • Short: nothing scrolls, nothing nests except the mouse chooser.
  • App and Learn read as two clear groups without a second menu.
  • Icon-only toggles need tooltips; the rail is tight below 520 px.

Best overview per click. New panel component (Radix popover rather than a dropdown menu), so a bit more work.

3

Everything inline, no submenus

A settings-sheet feel inside a menu. Each preference is a row with its control on the right: a switch per toggle, a compact segmented control for Theme. Mouse controls becomes a horizontal row of chips with the chosen preset's bindings underneath, so the description you get in a submenu today is still there. Help turns into a two-by-two grid of doc tiles, which reads faster than four look-alike rows.

  • No fly-outs at all: every state is set and seen in one place.
  • The chip row teaches the presets: the hint changes as you click.
  • Mixed control kinds in one menu need care with keyboard focus (Radix menus want menu items, not switches).

Richest at rest, most work to make accessible. Good fit if the owner wants the menu to feel like quick settings.

4

Control centre with search on top

The menu opens like a phone's quick-settings sheet. A search box is the first thing in it and takes over the Help menu's Search… item: typing finds commands and help pages alike, and the Ctrl+K dialog stays as it is. Under it, four tiles show Theme and the three toggles with their current value; Theme cycles on click. The mouse presets are a segmented row. Then the plain items in two short columns, and a version strip at the bottom with update state, GitHub and About.

  • Tiles make state readable from across the room; the whole thing fits in 460 px of height.
  • Search as the first row makes the menu the one place to go when lost.
  • Visually the furthest from a menu; the four-squares icon would want a new tooltip ("Menu and help").

Most playful, closest to the brand's "modern UI" line. Clear winner if help discoverability is the goal.
